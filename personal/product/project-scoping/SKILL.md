# Project scoping

## When to use
Use before committing to a new personal project or major feature, when shaping an MVP to test the highest-risk assumption, or when a request grows beyond its stated outcome.

## When not to use
Do not use for a small, already-scoped maintenance change.

## Personal principles
Prefer a clear useful outcome, a narrow complete loop over a broad incomplete platform, and explicit deferrals over feature volume.

## Workflow
1. Define user/problem, core assumption, and desired outcome.
2. Identify constraints, non-goals, dependencies, and risks.
3. Map the smallest end-to-end MVP path and remove features that do not test the central assumption.
4. Classify new or expanding requests as required, enabling, experiment, or deferred future idea.

## Decision rules
Choose the smallest scope that can test the central assumption; new work must earn its place by improving the current outcome or reducing a proven risk.

## Constraints
Do not turn unknowns into commitments without evidence; keep deferred ideas recorded separately.

## Failure modes
If the problem or user is unclear, pause scope expansion and clarify it.

## Expected output
Produce a problem statement, scope, non-goals, MVP, risks, and success criteria.

## Validation
Another person can explain what will and will not be built from the scope alone.
